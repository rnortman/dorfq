dorfq

A merge queue for large monorepos with long CI and high PR velocity.

Simulation results Source Run it License

What it does

DorfQ (Dorfman + queue, after Robert Dorfman's pooled testing) pools queued pull requests into batched CI runs, so one passing run lands many changes. When a batch fails, it infers the culprit from what failed instead of bisecting blind. It lands only the exact tree that passed CI, by fast-forwarding trunk.

Every belief is probabilistic. It reasons about false positives, false negatives and infrastructure flakes, and runs speculative batches when the expected value exceeds the cost.

Its state lives in git, in refs like refs/dorfq/…; there is no database, and it reconstructs its state from the repository on restart. Deploying it is running a single binary with access to your GitHub installation and bot credentials.

Is it for you

GitHub's built-in queue and the bisecting Bors variants hold up at a few pull requests an hour with ten-minute CI and few flakes. At 20+ pull requests an hour, CI that sometimes takes three hours, and a flake rate above a fraction of a percent, they fall over. DorfQ is built for the latter.

  • Once it accepts a pull request, it owns it until it lands or is handed back. Nobody babysits the queue.
  • Stacks and trees of pull requests are native, landed atomically or split as each stack says.
  • It models CI cost directly, and speculates only when the expected value exceeds it.

Status

DorfQ runs as its own merge queue. GitHub is the only forge supported; the forge interface is abstracted for others. Operational and developer tooling is still thin.
